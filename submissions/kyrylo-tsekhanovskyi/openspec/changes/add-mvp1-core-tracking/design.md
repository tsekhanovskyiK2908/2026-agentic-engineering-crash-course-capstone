## Context

Greenfield: `backend/` and `frontend/` do not exist yet. See `proposal.md` for the motivation and the
specs under `specs/` for the behaviour. The layout, launch, test and parallelism decisions are already
accepted in `docs/adr/0001`–`0009` and are not repeated here. This document covers the decisions the
makers need to implement the specs consistently. The HTTP surface is fixed in
`contracts/openapi.yaml`, and any change to it is escalated to the human.

## Goals / Non-Goals

**Goals:**
- One unambiguous contract that the backend and frontend makers can implement in parallel.
- Every scenario is traceable to a test, and every business rule has a database backstop where one is cheap.
- A walking skeleton first, so the parallel feature work starts from a green `npm run check`.

**Non-Goals:**
- Performance work beyond sensible indexes: MVP-1 data is a few hundred rows.
- A shared state-management library on the frontend.
- Optimistic concurrency: there is a single user.

## Decisions

### D1. Walking skeleton before features
The `## 1. Shared` tasks are done sequentially by the orchestrator:
- the solution with all projects and analyzers;
- the AppHost with PostgreSQL 17;
- the first migration;
- `/api/health`;
- SPA hosting;
- the Angular shell;
- contract type generation;
- the Playwright setup.

Only then do the makers start. *Alternative:* the makers scaffold their own side. That was rejected,
because both would need to touch the root `package.json`, `.gitignore` and the AppHost at the same time.

### D2. Persistence (DAL)
- EF Core code-first with Npgsql, and migrations in `BOMKeeper.DAL`.
- Ids are UUID v7, generated by the application (`Guid.CreateVersion7()`).
- UUID v7 is only ordered to the millisecond, so ids are **not** used for ordering. Every table has a
  database-generated `seq bigint GENERATED ALWAYS AS IDENTITY` column. "In the order added" is
  `ORDER BY seq`, and "newest first" is `ORDER BY seq DESC`. `seq` is never exposed by the API. Only
  Project stores `createdAt`, because the spec shows it.
- Enums are stored as strings, for readable data and a safe reordering of enum members.
- Money is two columns, `amount numeric(12,2)` and `currency char(3)`, mapped as an EF complex/owned
  value. A missing price means both columns are null.
- Foreign keys use `ON DELETE CASCADE`: Project→Item, Project→Listing, Item→Offer, Listing→Offer.
  PostgreSQL allows these multiple cascade paths.
- Database backstops for the BLL rules:
  - a unique index on `offer(item_id, listing_id)` (`duplicate-offer`);
  - a partial unique index on `offer(item_id) WHERE is_chosen` (one chosen offer per item).
  - The same-project rule is enforced in the BLL only. *Alternative:* a composite foreign key that
    includes `project_id` on offers; rejected as schema complexity that isn't needed for MVP-1.
- The DAL exposes repository interfaces plus a unit-of-work (`SaveChangesAsync`). The BLL depends
  only on those interfaces.

### D3. Business logic (BLL) and error model
- One service per capability: projects, items, listings, offers, and the summary.
- Validation is plain code in the BLL (no validation library). It collects field errors keyed by
  the JSON property path (`name`, `askingPrice.amount`).
- Errors are exceptions defined in the BLL: `ValidationFailedException` (field errors),
  `NotFoundException`, and `BusinessRuleException(code)`, where the code is `duplicate-offer` or
  `listing-in-other-project`. *Alternative:* `Result<T>` return values; rejected, because controllers
  stay thinner when the Api maps every error in one place.
- Choosing an offer uses **ordered writes inside one transaction**, because PostgreSQL checks the
  partial unique index (D2) per statement. A partial unique index can't be deferred, and EF does not
  guarantee the order of the UPDATEs within one save:
  1. clear the item's current choice (`is_chosen = false` where `item_id = @item and is_chosen`), and save;
  2. set `is_chosen = true` on the target offer, and save;
  3. commit.

  Un-choosing is step 1 only. The switch is tested in both directions against PostgreSQL (offers:
  Switching back and forth).
- Currency codes are validated against a static list of **active ISO 4217 codes** kept in the BLL (a
  snapshot of the ISO 4217 list, with its date in a comment). The list does not depend on ICU or
  culture data, which is unavailable in invariant-globalization containers. The contract states the
  `^[A-Z]{3}$` shape, and the BLL additionally rejects unknown codes such as `ZZZ` (ADR 0002).
  Human decision of 2026-09-30: the list holds circulating currencies only. The special ISO 4217 codes
  (XXX, XTS, the metals XAU/XAG/XPT/XPD, the bond units XBA–XBD, XDR, XSU, XUA, and the fund codes such
  as BOV, CHE, CHW, CLF, COU, MXV, USN, UYI, UYW) are excluded.
- Time comes from an injected `TimeProvider`, so `createdAt` and `statusChangedAt` are testable.
- The summary is computed in memory from the project's items and offers, with `decimal` arithmetic.
  Totals are ordered by currency code.

### D4. HTTP API
- ASP.NET Core controllers in `BOMKeeper.Api`. Route names equal the contract `operationId`s (for
  example `[HttpGet(Name = "listProjects")]`), so the generated document can be compared with the contract.
- JSON uses camelCase. Enums are strings (`JsonStringEnumConverter`). Money amounts are JSON numbers.
- One `IExceptionHandler` maps the BLL exceptions to RFC 9457 problem details:
  - validation errors → `400` with `errors`;
  - `NotFoundException` → `404`;
  - `BusinessRuleException` → `409` with `type: "/problems/<code>"`.

  Model-binding errors (for example an unknown enum value) also return `400` problem details.
- The problem responses match the contract schemas:
  - `ValidationProblemDetails` always has `errors`, `title` and `status`;
  - a `409` uses `RuleViolationProblemDetails`, which always has a non-null `type`, `title` and `status`.

  The Api uses its own problem types, or OpenAPI schema transformers, so that the generated document
  has the same schema names and `required` lists as the contract.
- Request DTOs carry DataAnnotations that mirror the contract bounds (`[StringLength]`, `[Range]`,
  `[RegularExpression]`), so the generated document contains the same constraints and malformed input
  is rejected at binding. The BLL stays the authority for every rule and is where the rules are
  unit-tested, including the rules that DataAnnotations also cover.
- `PUT` replaces all editable fields of a resource. `PATCH` is used only for the status, fit and
  choice sub-resources, each with a one-field body.
- The OpenAPI document is generated by `Microsoft.AspNetCore.OpenApi` at `/openapi/v1.json`.
- `/api/health` is mapped with ASP.NET health checks from `ServiceDefaults`. It is infrastructure,
  not part of the contract, and it is excluded from the drift comparison.

### D5. Contract-drift test
An integration test fetches `/openapi/v1.json` and compares a **normalized** view of it with
`contracts/openapi.yaml`. Both documents are reduced to the same structure, and the two structures
must be equal. The normalized structure contains exactly the following, and nothing else:

- **Operations:** every path under `/api/` except `/api/health`, with its HTTP methods. For each operation:
  - `operationId`;
  - the path parameters (name, `required`, JSON type);
  - the request body: `required`, its media types, and the schema of each;
  - the responses: the status codes; for each, its media types and schema, and its header names
    (for example `Location` on `201`).
- **Schemas**, compared recursively, including inline schemas, array `items`, `additionalProperties`
  and the non-null branch of a `oneOf`/`anyOf` with `null`. For each:
  - a named component schema is compared by name, and its body once;
  - JSON type, with `null` removed;
  - nullability, as a boolean, however it is spelled (`type: [x, "null"]`, `oneOf` with `{type: null}`,
    or `nullable: true`);
  - the property names;
  - `required`;
  - `enum`;
  - `minimum`, `maximum`, `minLength`, `maxLength` and `pattern`.

**Excluded:** `info`, `servers`, `security`, `tags`, `summary`, `description`, `example(s)`, `format`,
`multipleOf` (the generator can't express it; the BLL enforces two decimal places), `x-*` extensions,
the order of keys and array elements, and the bodies of `204` responses.

Any difference in the normalized structure fails the test and prints the differing paths.
*Alternative:* a byte-for-byte comparison; rejected, because the generator's formatting would make it
flaky. *Alternative:* generating the contract from code; rejected, because it would not be contract-first.

### D6. Frontend
- Angular 22 with standalone components, signals, the new control flow, and Angular Material.
- Routes:
  - `/projects`;
  - `/projects/:projectId` (tabs "Items" and "Listings", and a summary card);
  - `/items/:itemId`;
  - `/listings/:listingId`.
- API types are generated by `openapi-typescript` from `contracts/openapi.yaml` into
  `src/app/api/schema.d.ts`, using the `generate:api` script. `check:fe` fails if the generated file is
  out of date.
- There is one typed `HttpClient` service per resource: projects, items, listings, offers.
- Components hold state in signals and reload from the API after each mutation. There is no global
  store. *Alternative:* NgRx signal store; rejected as more than MVP-1 needs.
- Forms are typed reactive forms in Material dialogs. Server `400` errors are shown on the matching
  form fields.
- Deleting asks for confirmation.

### D7. Traceability of tests to scenarios
Each test names the scenario it covers, using the capability and scenario title:
- xUnit: `[Fact(DisplayName = "offers: Choosing switches the choice")]`;
- Vitest and Playwright: `it('offers: Choose an offer from the item page', …)`.

A checker can grep a scenario title to find its test.

Test levels:
- `[BLL]` → `BOMKeeper.BLL.Tests`, with hand-written fakes of the DAL interfaces.
- `[API]` → `BOMKeeper.Api.IntegrationTests`, using `WebApplicationFactory` and one Testcontainers
  `postgres:17` per test collection. Migrations are applied once, and tables are truncated between tests.
- `[FE]` → Vitest with TestBed and `HttpTestingController`.
- `[E2E]` → Playwright against the stack launched by the AppHost.

## Risks / Trade-offs

- **The contract-drift comparison is too strict or too loose** → the normalization rules are fixed in
  D5. A mismatch is fixed in the code, or escalated as a contract change; it is never fixed by
  loosening the comparer silently.
- **The generator can't express something in the contract** (for example the decimal format) → the
  contract uses plain `number`. Formats are outside the comparison (D5).
- **Docker is required** for the integration and e2e tests → `check` reports a stopped Docker clearly
  (ADR 0005).
- **Makers at low effort drift from the spec** → the contract, the `[checks]` tasks with red evidence,
  and the cross-vendor reviews constrain them. The retry-stop rule escalates to high effort.
- **Parallel makers need data from each other** → the frontend never needs a running backend for unit
  tests. Only the `## 13` e2e task waits for both.

## Migration Plan

Greenfield. The first EF migration creates the schema. Development data lives in the
`bomkeeper-data` Docker volume; deleting the volume resets it. Rollback is `git revert`.
